# Архитектура и правила

## Граница приложения

Один оператор владеет бизнес-записями (`tenant_id`). Владелец физической конструкции — отдельная организация (`owner_id`). Конструкции и рекламные поверхности — отдельные сущности. Рекламные кампании и продажи не входят в эту версию.

Браузер получает состояние через авторизованный `GET /api/app`. Изменения идут через `POST /api/app` с `action`, `payload` и ключом идемпотентности. API не принимает произвольные названия таблиц или SQL. UI-права дополнительно проверяются в сервисе для каждой операции; скрытая кнопка сама по себе не считается защитой.

## Транзакции и конкурентные изменения

Выполнение команды блокирует строку оператора `FOR UPDATE`. Это простая последовательная модель для одной компании; при дальнейшем масштабировании её можно заменить блокировками отдельных объектов. В этой транзакции проверяются роль, принадлежность, версия, переход статуса, связанные записи и файлы; обновляются состояние, история, уведомления и результат идемпотентности.

Ключ идемпотентности уникален по оператору и сотруднику. Повтор того же запроса возвращает сохранённый результат. Использование того же ключа с другим содержимым отклоняется. Клиент сохраняет ключ до подтверждённого ответа, поэтому разрыв связи не приводит к повторному созданию записи. `version` защищает карточки, документы, дефекты, осмотры и задания от молчаливой перезаписи; конфликт возвращает HTTP 409. Планировщик берёт такую же блокировку и использует уникальную пару `(plan_id, due_at)`.

Завершение осмотра и создание всех его результатов/дефектов выполняются атомарно. Ошибка даже в последнем пункте откатывает всю операцию. При принятии ремонта транзакция закрывает только выбранные связанные дефекты. Техническое состояние вычисляется из текущих дефектов и результатов, а не хранится как устаревающий цвет маркера.

## Расчёт технического состояния

1. Любой активный критический сигнал или подтверждённый критический приоритет → критическое состояние.
2. Подтверждённый активный дефект серьёзности «ремонт» → требуется ремонт.
3. Незначительные активные замечания → есть замечания.
4. Непроверенные сообщения, отсутствие осмотра или непроверенные пункты последнего осмотра → неизвестно.
5. Подходящий осмотр без нерешённых пунктов → исправно. Замечания последнего осмотра считаются устранёнными только после подтверждённого закрытия связанных дефектов.

Срок осмотра и состояние документов вычисляются отдельно. Просроченный документ не меняет техническое состояние. Ручное уточнение допускает только неизвестное состояние/замечания/ремонт, требует причины и аудита, не скрывает критический сигнал; новый дефект и новый осмотр сбрасывают ручное уточнение. UI не даёт произвольно назначить «исправно».

## Роли

| Операции | Роли, кроме администратора |
| --- | --- |
| Карточки, владельцы, документы | Менеджер |
| Назначение осмотров и планы | Менеджер, диспетчер |
| Завершение назначенного осмотра | Инспектор |
| Сообщение о дефекте | Менеджер, диспетчер, инспектор, техник |
| Разбор дефектов, создание/отмена работ | Диспетчер |
| Принятие/начало/пауза/отчёт работы | Назначенный техник или инспектор |
| Проверка работ | Менеджер, руководитель; обязательно другой сотрудник |
| CSV | Менеджер, диспетчер, руководитель, наблюдатель |
| Пользователи, роли, справочники, аудит | Администратор |

В текущем MVP все активные сотрудники оператора могут читать его объекты. Индивидуальные списки разрешённых объектов для наблюдателя пока не настраиваются. Контактный email сотрудников скрыт от инспектора, техника и наблюдателя. Доступ к API, загрузкам, выгрузкам и QR требует сессии.

## Документы и файлы

Документ с `expires_at = NULL` бессрочный. Требования — внутренний справочник компании с текстом основания; правовые нормы не зашиты. Продление создаёт новый документ и связь версий, а прежний остаётся доступен. Незаметной замены проверенного файла нет: API обновления содержимого вложения отсутствует.

Для локального файла `/api/files/:id` проверяет сессию, выдаёт ссылку на 60 секунд и повторно проверяет сессию/подпись при чтении. Supabase использует `createSignedUrl` после серверной проверки. Бакет закрыт; service-role ключ доступен только серверу. Размер ограничен 10 МБ; SVG разрешён только для собственных демоиллюстраций, пользовательская загрузка SVG/HTML/JS запрещена. Антивирусная проверка и удаление метаданных EXIF не реализованы.

## Офлайн-черновики

Форма осмотра и отчёт работы сохраняются в `localStorage` с ключом сотрудника. Они восстанавливаются в той же форме после входа. Локальное сохранение не меняет серверное состояние. При повторной отправке сохраняется идемпотентность, а при конфликте нужно обновить данные и разрешить расхождение. Выход предупреждает о черновиках и удаляет локальные служебные данные данного пользователя. Файлы загружаются отдельно: офлайн-хранение новых бинарных вложений и автоматическая синхронизация в фоне не реализованы.

## Отчёты

- Действующие объекты: подтверждённые карточки, жизненный цикл не «демонтирована».
- Открытые дефекты: статус не «закрыт», «отклонён», «дубликат».
- Просроченные работы: срок прошёл, статус не «выполнено»/«отменено».
- Время устранения: UTC-время подтверждённого закрытия минус UTC-время регистрации. Среднее считается только по закрытым; число открытых показывается рядом.
- Расходы: сумма точных значений `work_materials.cost`, где стоимость — итог **строки**, а не цена единицы. Денежные поля PostgreSQL `numeric(16,2)`; выгрузка суммирует целые копейки и форматирует две десятичные цифры.

Время хранится как `timestamptz` и отображается в часовом поясе оператора. По умолчанию `Asia/Qyzylorda`.
